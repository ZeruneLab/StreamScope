# StreamScope 视频深度分析实施方案与计划

状态：核心实施已完成，扩展验收继续推进。0.1.5 已接入基础工作台、可信度校准、H.264 深度数据，以及 H.265 的实际 CTU、叶子 CU/PU/TU；未取得的数据不生成伪值。

基线：StreamScope 0.1.5；面向 Windows 桌面、H.264/H.265、实时 RTSP、PCAP/PCAPNG 与视频文件。

## 1. 目标与决策

在 StreamScope 自有界面中完成视频播放、逐帧分析、语法查看、编码块可视化、异常定位和报告导出。用户可以从一处画面异常追溯到帧、NALU 和 RTP 包，反向也可以从异常包定位受影响画面。

采用“现有 Rust 分析链路 + 现代 FFmpeg 数据提取 + 自有 React 分析工作台”的路线。参考 VideoEye 的分析交互和数据组织，参考 H.264 Analysis 的头部语法解析，不将两个旧 MFC 工程整体并入桌面程序。

基础能力独立实现；Elecard 作为可选对照工具或后续可选分析后端，不作为首版必要依赖。是否能分发 Elecard 引擎、是否提供 SDK，仍需厂商书面确认。

首轮先覆盖 H.264/H.265 渐进式 4:2:0 视频；H.264 常用 Baseline/Main/High、H.265 Main/Main10 进入测试矩阵。对隔行、特殊色度格式、多层编码等不能完整分析的输入明确提示能力边界，基础解码与深度分析支持范围分别显示。

## 2. 已核实基础与尚未解决的问题

### 2.1 StreamScope 现状

- 已有实时 RTSP、TCP Interleaved/UDP、PCAP 多流识别、RTP 序列统计和媒体重组。
- 已有 H.264/H.265 NALU、部分参数集、关键帧/GOP 统计与帧证据。
- 帧证据包含 RTP 时间戳、首尾序号、抓包包号、裸码流字节区间及边界可信度。
- 已有视频预览、解码日志、部分画面异常扫描和跨层报告。
- 已有 H.264 QP/MV、实际宏块/子宏块分区、逐 8×8 参考索引/参考 POC，以及 H.265 CTU、叶子 CU/PU/TU、最小 CB QP 网格的数据模型与精确帧工作台；尚无 H.264 逐变换块/残差树，也未导出 H.265 残差系数值。
- H.264/H.265 裸流结构分析和选中帧语法读取已改为流式读取；逐帧 ffprobe 索引仍最多保留 50,000 帧，并在超过上限时明确记录部分覆盖。

### 2.2 VideoEye

已检查原始仓库中的 `ve_play.cpp`、`Dfanalysis.cpp`、`Dfanalysis.h`：读取旧版 FFmpeg 的 `qscale_table`、`mb_type`、`motion_val`、`ref_index`，绘制 QP、宏块类型、运动矢量、参考索引，并有图片/CSV 输出逻辑。

这些代码证实 H.264 块级可视化有具体实现参考，但依赖旧版 FFmpeg 结构与 MFC。宏块类型标记不必然包含全部子分区细节，参考索引也不等于实际参考帧标识，移植时需要重新验证语义、坐标、步长和帧对应关系。

### 2.3 H.264 Analysis

已检查 `NALParse.cpp` 与 `h264_stream.cpp`：适用于 NALU、SPS/PPS/SEI、Slice Header 等解析与呈现。其 Slice Data 实现存在明确的未实现部分，不能作为完整 CABAC/CAVLC 宏块分析器。

### 2.4 当前随包 FFmpeg 实测

- 对项目 H.264 样本开启 `venc_params+mvs` 后，10 个解码帧存在编码参数附加数据，P 帧存在运动矢量附加数据。
- 现代 FFmpeg 的 H.264 编码参数接口定义了基础 QP 与逐宏块差值，可据此获取实际宏块亮度 QP。
- 定制 FFmpeg 9.0.1 已通过 H.265 Main、Main10/WPP 和 FFmpeg FATE `TILES_A_Cisco_2.bit` 真 Tiles 样本导出 CTU、叶子 CU、实际 PU、叶子 TU和最小 CB QP，并用 H.264 I/P/B 样本回归公共 MV 与同帧身份。真 Tiles 样本暴露的低延迟帧过早入输出队列问题已修复：请求编码参数 side data 时，当前帧必须完成块导出后才能进入输出队列。
- 已完成 30 列 CSV 模式、补丁对干净源码的应用验证、静态 worker 构建，以及 H.265 Main、Main10/WPP、多 Slice、CRA/RASL 和 Tiles 基础树级回归；24 帧 Main10/WPP/多 Slice/open-GOP 样本逐帧均导出完整 CTU 层。尚未完成全部 Profile、Tiles 逐块外部真值对照和两小时压力验收。

结论：H.264 QP/MV/宏块与子宏块分区、参考列表索引及逐 8×8 参考 POC 路线已落地；H.265 已通过解析期插桩取得实际 CTU、叶子 CU/PU 和有变换语法的叶子 TU，并完成真 Tiles 样本基础导出验证。当前剩余边界是残差系数、Tiles 逐块外部真值对照、Main10/WPP 扩大样本矩阵及损坏流压力验证，不能把“树已导出”扩大解释为这些能力也已完成。

## 4. 系统架构与模块分工

处理链：输入与流选择 → 原始数据落盘/索引 → RTP 重组与 NALU/AU 识别 → 帧索引与解码 → 按需深度分析 → 诊断与界面/报告。

保留当前模块职责：

- `crates/capture`、`crates/rtsp`、`crates/rtp`：媒体源、流身份、包级证据与落盘。
- `crates/h264`、`crates/h265`：码流语法、AU 边界、参数集版本和字节来源。
- `crates/core`：通用视频帧、块、参考关系和分析范围模型。
- `crates/analyzer`：调度、任务状态、异常片段、各层证据关联。
- `crates/diagnostics`、`crates/report`：结论、证据、验证建议、导出。
- `apps/desktop`：分析工作台和交互。

新增后台 `video-worker` 工具，使用匹配版本的 libavcodec/libavutil 做软件解码和数据导出。建议采用小型 C/C++ 程序，Rust 通过管道或本地结果文件调用。UI 控制信息走小型结构化消息，图像与大量块数据走有界缓存/磁盘文件。

选择独立进程是为了隔离损坏流、资源峰值和解码器故障。Windows 启动隐藏控制台，任务支持取消、超时、错误返回；错误和日志最终显示在 StreamScope 中。

系统不跨 ABI 直接读取 FFmpeg 内部结构。必须使用内部信息时，在固定版本解码器内添加导出点，再通过我们定义的数据格式输出。版本与补丁作为构建输入记录。

## 5. 统一索引与数据可信度

### 5.1 核心记录

| 记录 | 关键字段 |
|---|---|
| Source/Stream | 源指纹、流 ID、端点、SSRC、会话阶段、编码类型 |
| Packet | 原始包号、扩展序号、到达时间、RTP 时间戳、负载位置 |
| NALU | 类型、完整性、原始来源区间、重组字节区间、参数集版本 |
| Access Unit | AU ID、包含的 NALU、边界依据、缺失/损坏状态 |
| Frame | 解码/显示索引、POC、PTS/DTS 与时间基、AU 关联、解码错误状态 |
| Block | 帧 ID、坐标/尺寸、块层级、QP、预测类型、矢量、参考目标 |
| Finding | 区间/区域、类别、直接证据、候选推断、覆盖范围、验证方法 |

帧键至少包含任务、流、会话阶段和帧索引；POC/RTP 时间戳会回绕或重置，不能单独充当唯一标识。

RTP→NALU、NALU→AU、AU→解码帧使用显式关联表。保留真实包号集合或分段区间，不能将首尾包号之间的所有包都判为属于该帧。聚合包可对应多个 NALU，分片 NALU 可对应多个包；丢弃、场图像及损坏输入不强行一对一。

### 5.2 时间与像素坐标

- 抓包时间、RTP 媒体时钟、解码顺序、显示顺序分开存储。
- 没有原始 PTS/DTS 时，推导值保存方法和可信程度；不伪装成原始字段。
- 块坐标使用编码图像坐标，UI 明确处理裁剪、宽高比、旋转和缩放。
- 10-bit 与 8-bit、有限范围与全范围分别处理；分析数据来自原始解码输出，预览色彩转换不改变分析依据。
- 记录解码器错误隐藏及参考缺失。成功产生画面不自动等于原始码流完整。

### 5.3 分析覆盖范围

分别记录接收/读取、保留、结构解析、成功解码、块级分析、画面扫描和预览覆盖范围。不使用一个完成百分比概括所有层。

缺失值使用 `null` 和原因；不支持、不适用、数据损坏、尚未分析分别表示。不能用 0 代表未测得 QP/MV，也不能把 Slice 初始 QP 当作整帧实际 QP。

## 6. 编码分析路线

### 6.1 H.264

1. 使用现代 FFmpeg 公共 side data 提取实际宏块 QP 与可用运动矢量。
2. QP 按基础值与块差值还原，分别标记亮度/色度语义；范围由位深和编码类型决定，不固定写死为所有输入均 0–51。
3. MV 保留原始整数、缩放因子、源/目标坐标和方向。方向标记不直接当成完整参考帧 ID。
4. 对公共接口缺少的宏块类型、参考列表、分区数据评估小范围导出补丁。数据应在生命周期结束前复制或持有有效引用。
5. 引入 B 帧、多个 Slice、MBAFF/隔行等测试后逐项放开支持，不能由逐行样本推断全部格式已支持。

### 6.2 H.265

1. 先完善 VPS/SPS/PPS、Slice Header、POC 和随机访问相关证据。
2. 在软件解码器解析 CU、PU、TU 与重建参考关系时导出观察数据。优先输出最终块树、实际 QP、最终 MV 和参考目标。
3. 记录 CTU→CU→PU/TU 层级，支持不等大分区；不能套用 H.264 固定 16×16 网格。
4. 正确处理 merge/skip 派生值、双向预测、Main10、Tiles/WPP，并分别验证导出线程一致性。
5. B 帧延迟输出、CRA/RASL、丢失参考和中途入流必须纳入回归。
6. 如固定版 FFmpeg 插桩无法稳定覆盖要求，评估参考解码器或有明确接口和授权的后端；通过小样本质量/速度/许可验证后再决定，不提前承诺替换即成功。

软件解码作为第一轮深度分析基准。硬件解码可用于播放，但不假定其暴露相同内部数据。

## 7. 实时、文件和抓包流程

### 7.1 文件

先建立轻量帧/NALU索引，再对用户选中帧或时间段做块级分析。裸流优先；MP4/MKV 通过解封装接入同一模型。保留原始容器时间与 extradata，并记录 Annex B 转换中的偏移映射。

全文件分析为显式任务，可取消和查看进度；长文件不能受 60 秒预览上限限制。若仍存在保留或解码上限，UI 明确显示实际覆盖，不能标成全量完成。

### 7.2 PCAP/PCAPNG

扫描多流 → 选择一路或多路 → 为各路建立独立媒体索引 → 按需深度分析 → 帧/异常/包号联动。

TCP 重组、RTP 乱序和 SSRC 重用均保留原有证据。通过 SDP 补入的参数集标记来源，不计为抓包中实际出现的 NALU。不把不同流或重启阶段合并到同一参考图像状态中。

### 7.3 实时 RTSP

接收线程持续落盘并产生轻量统计；解码与深度分析使用独立队列。默认轻量监控，用户选中区间或异常触发后执行块级分析。

异常片段按时间预算保留，但解码起点回溯到合适的随机访问位置并保留参数集及依赖上下文。开放 GOP、CRA 前导图像或无关键帧场景必须显示上下文不足。

处理速度低于输入速度时显示积压、估计分析延迟和覆盖范围；优先减少自动深度分析负载，不能把分析排队直接算成网络丢包。数据盘达到上限、空间不足或写入失败时明确报警并记录停止位置。

当前已有落盘能力可复用；本计划补充随机访问索引和分析窗口。崩溃恢复、无限时长采集、循环删除旧段不作为默认附带功能，需另设验收范围。

## 8. UI 设计

新增“视频深度分析”入口，保留现有音频质量和音画同步入口。

| 区域 | 内容与交互 |
|---|---|
| 左侧 | 视频流、会话阶段、异常列表和筛选 |
| 中间 | 逐帧画面、缩放、原始/Y/U/V 分量、选区、叠加层 |
| 右侧 | 当前帧参数、语法树、块详情、参考帧 |
| 下方 | GOP/帧大小、码率、QP 统计、异常时间线 |

选中帧统一驱动全部面板；选中块显示坐标、尺寸、QP、预测类型、矢量及可用参考帧。不同层级单独开关，图例注明单位与色标。

普通视频控件用于连续播放；精确逐帧画面由解码索引返回，不能仅依靠 `currentTime` 定位。点击已有异常定位到精确帧失败时显示候选范围，不悄悄定位到相邻帧。

无块级数据时展示原因。对未知块不画代表正常值的颜色。实时分析中持续显示媒体覆盖区间、深度分析进度和积压。

## 9. 故障分析和报告

首批规则：RTP 缺口与 FU 不完整、参数集缺失/变化、解码错误、参考缺失、关键帧等待、黑屏/冻结候选、局部色块/条带候选，以及错误后持续异常和恢复候选。

每项报告包含：异常是什么、何时何地发生、涉及哪些帧/包、直接证据、推断及替代解释、影响范围、建议和验证步骤。保存前后画面及定位信息。

丢包不必然导致花屏；QP 高不等于码流损坏；冻结可能是静态场景；到达 IDR/CRA 不证明实际恢复。单次抓包不能排除抓包端自身丢包。不能在缺少解码器块级错误证据时，把一个丢失 RTP 包精确归因到某个像素块。

参考关系可以给出潜在传播范围；只有结合实际画面/解码证据才能收紧为观测影响范围。数值置信度未经标注数据校准前，使用“确认观测/候选/证据不足”等分级。

主报告保留摘要和关键证据；全部帧/块数据存独立索引与可选证据包。静态 HTML 提供精选图像和表格，不把数百万编码块内联进去。导出内容标明原始样本、补入信息、分析器版本和覆盖区间。

## 10. 性能与存储

采用磁盘索引保存帧/NALU与来源关联，可使用 SQLite；编码块数据按帧分块存储并按需读取。普通分析只存统计，详细块数据默认仅保留选中区间和异常窗口。

缓存采用有界队列和 LRU；绘图按缩放级别裁剪/降采样，数值查询仍访问原始数据。取消后停止工作进程并保留已完成索引的明确状态。

以下为 P0 后校准的目标，不是已测成绩：

- 基准机：记录 CPU、内存、磁盘、系统及分析器版本，至少覆盖 16 GiB 内存环境。
- 1080p 单流轻量分析争取达到输入速度；4K/Main10 和完整块级分析实测后标注处理倍速。
- 已缓存帧切换目标小于 200 ms；冷定位耗时随参考帧距离变化，应给出进度。
- 活跃缓存初始预算 512 MiB，可在 P0 调整；解码器参考帧、GPU 和索引开销另行统计，不能称整个进程仅用 512 MiB。
- 取消请求目标 2 秒内生效，超时子进程受控退出。
- 2 小时压力测试中内存不随帧数持续线性增长；磁盘增长符合保存策略。

## 11. 测试与验收

### 11.1 样本矩阵

- H.264：Baseline/Main/High，CAVLC/CABAC，I/P/B，多 Slice，裁剪、分辨率变化、不同 GOP。
- H.265：Main/Main10，I/P/B，IDR/CRA，Tiles/WPP，多 Slice，参数集更新。
- 格式边界：隔行/场图像、特殊色度、多层/扩展格式至少验证不会被误报为完整支持。
- 网络：UDP/TCP、聚合/分片、乱序、重复、丢包、回绕、重启、多流相同 SSRC。
- 损坏：截断 NALU、缺参数集、缺参考、错误 Slice、抓包截断。
- 画面：正常静态场景、镜头切换、合法纯色/黑场、噪声、真正花屏、冻结、条带。

### 11.2 正确性

1. 使用同一原始样本比较帧顺序、AU 边界、关键参数和块数据；不要用重编码预览作码流分析输入。
2. 用独立可信分析器或可验证测试向量对照 QP、分区、MV 单位与参考目标。仅比较同一提取器自己的两次输出不算正确性验证。
3. 为丢包注入记录真值，要求报告定位到对应流和包，受影响 AU 正确；像素影响范围按可获得证据验收。
4. 参考比对必须处理 B 帧重排、裁剪、位深、颜色范围、时间偏移和丢帧。
5. 正常样本记录误报率，异常样本记录检出率、漏报、定位偏差及不确定项；指标阈值在 P0/P3 基于样本集制定。
6. 旧版报告可打开，现有音频分析/导出/同步回归通过，未支持数据不生成伪值。

### 11.3 稳定性与打包

验证超时、取消、磁盘满、分析进程退出、格式变化、大文件与多流并发。新增能力在干净 Windows 环境验证，用户不需安装编译器或单独安装分析 DLL。报告记录实际生效的分析器版本，缺组件时有明确提示。

## 12. 分阶段实施计划

工期为有效工程投入估算，不是日历承诺。默认有一名熟悉 Rust/Tauri 的开发者，块级阶段有 C/C++/编解码经验支持；P0 完成后更新估算。下列版本仅为建议里程碑。

| 阶段 | 工作与交付 | 阶段验收门槛 | 估算 |
|---|---|---|---|
| P0 技术验证 | 固定依赖、样本集、许可证清单；H.264 块数据提取原型；H.265 导出点验证；索引设计 | 实际坐标/QP/MV 可读取并有外部对照；记录不支持项；决定 H.265 后端 | 1–2 人周 |
| P1 基础工作台 | 统一索引、逐帧图像、GOP/帧图、基础语法树/HEX、流选择与包反查 | 三类输入共用入口；显示与解码顺序正确；多流隔离；长文件按需定位 | 2–3 人周 |
| P2 H.264 可视化 | QP/MV、色标、鼠标详情、统计与导出、参数变化 | 可验证 QP 与 MV 数值/坐标；缺数据明确显示；B 帧样本通过 | 2–3 人周 |
| P3 H.264 深化与诊断 | 宏块类型/分区、参考关联、异常窗口、传播候选、完整证据报告 | 已声明支持范围逐项通过；丢包和画面证据联动；正常场景误报评估 | 2–4 人周 |
| P4 H.265 块级 | CU/PU/TU、QP、MV/参考导出、Main10/Tiles/WPP、UI 复用 | 与可信结果对照；不把固定网格当实际分区；复杂样本和损坏流稳定 | 6–12 人周，P0 后复估 |
| P5 质量与模型 | 参考视频对比、部分 DPB/HRD 检查、传播/恢复完善 | 对齐可靠；缺必要时序不输出缓冲合规结论；声明规则覆盖 | 3–5 人周 |
| P6 发布验收 | 性能、2 小时压力、干净机安装、兼容、文档与依赖材料 | 安装即用；资源有界；既有音频与报告无回归；可追溯发布构建 | 1–2 人周 |

建议交付批次：M1=P0+P1，形成可用工作台；M2=P2+P3，形成 H.264 深度分析与诊断；M3=P4，补齐声明范围内的 H.265 块级功能；M4=P5+P6，完成质量/缓冲增强与发布验收。每个批次都保留 H.264/H.265 已有基础功能，H.265 基础工作台不必等到 P4 才交付。

P0 失败时的处理：数据字段未验证的功能不列入已完成；公共接口不足转为明确补丁任务；商业 SDK 或其他后端仅在验证接口、许可、成本后进入计划。每一阶段都有可审查产物，不把全部任务压到最终一次交付。
