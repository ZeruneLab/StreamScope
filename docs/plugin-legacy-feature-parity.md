# 插件版旧功能恢复与验收（2026-10-09）

## 原则与问题原因

插件化改变安装、依赖和执行边界，不缩减原来已经存在的操作能力。此前核心预览使用简化的声明式页面，只显示少量结果区块；旧版完整工作台虽仍在源码中，但没有进入核心前端。这导致功能看起来被删除，甚至需要把抓包文件手工填到视频插件中。

本次核心前端重新使用宿主维护的完整工作台。`application-api.ts` 将业务动作转发给已启用、清单声明过动作的独立插件；核心只承担任务、产物、JSON/HTML 报告和受保护的文件保存。核心 Rust 依赖树仍没有 analyzer、ONVIF、SIP、FFmpeg 等业务模块，安装包仍只有主程序与 WebView2Loader。不是取消插件化或把分析器重新链接进主程序。

SIP 接收型模拟器按用户此前确认的“根据抓包向指定设备模拟，类似 SIPp，不需要接收”方向，不放入核心插件版主流程。兼容版原代码仍保留。它不是这次插件拆分造成的遗漏。

证据不足时仍拒绝猜测。例如 standalone H.264 的某些旧报告没有可靠 Access Unit 映射，不能仅按显示帧号伪造语法关联；真实抓包选流报告的唯一字节范围映射已验证。

## 完整数据与安全边界

- 主结果读回完整 JSON，而不是插件前 500/1,000 条展示摘要。原结果文件不批量修改。
- 视频块/语法等大结果存为 SHA-256 JSON 产物，插件管道只传引用；5 MiB 产物完整性及目录越界测试通过。
- 大 SIP 报告与导出输入也走文件产物。20,000 条 SIP 消息（JSON 大于 4 MiB）解析、完整读取和脱敏导出测试通过，没有调大管道限制或丢掉剩余消息。
- 重复使用已有只读样本时验证 SHA-256，避免被误判为“不能再次导入任务产物”；篡改仍拒绝。
- 原生插件没有系统级沙箱。安装必须确认签名、指纹和权限，不绕过换密钥确认。

## 本地交付和验证步骤

核心仍标记 **v0.1.10 预览版**，本轮四个增补插件版本为 **0.1.11**：audio、rtsp、sip、video-deep。不要仅更新主程序，否则新按钮的动作不在旧插件清单中，会提示未声明动作。其他原有包和共享 FFmpeg 依赖继续使用。

本轮提供核心 NSIS 安装器和一套新的本地签名 `.ssp` 验证包。新包使用临时测试发布者密钥，指纹见包目录“先读我.md”；与已安装预览包的密钥不同，导入时需要重新核对和确认。不是正式 GitHub Release，也没有自动替换安装版或写入本机插件注册表。

1. 关闭 StreamScope 后安装核心包，保留报告和插件数据。
2. 插件管理中导入这四个 0.1.11 包，阅读权限并确认新的发布者指纹；共享运行时已安装时不必重复安装。
3. 在 PCAP 页面扫描抓包，从流列表选择具体流并点击“深入分析此流”。不要把 `.pcap` 当作原始视频文件填入视频深度插件。
4. 视频流在同一结果工作台检查回放、深度、QP/运动矢量、语法/HEX；音频流检查质量、时间轴、搜索、格式/区间导出。
5. 检查 ONVIF→RTSP、SIP→PCAP、旧报告重开和原有更新入口。

后台测试命令：`node scripts/verify-workbench-parity.mjs`（保存报告作为只读 UI 测试数据、模拟 IPC）；`node scripts/verify-plugin-ui-layout.mjs`（辅助/第三方页面及联动）；`node scripts/verify-delivery-parity.mjs <包目录>`（隔离安装和真实九路抓包）；`node scripts/verify-core-host.mjs`（依赖和安装负载）。另有核心、兼容桌面、插件宿主和媒体/SIP 插件 Rust 回归。

这些证据支持“恢复完整功能入口并接回插件工作流”，不支持“所有设备、所有编码和所有历史操作已完成生产级验收”。正式 v0.2.0 发布、受控发布密钥及在线插件目录仍是独立未完成项。
