# 媒体插件联合分析修复（2026-10-09）

## 原因与修改

插件迁移版原先只提供独立文件表单。PCAP 的重组样本与每路结果没有交给视频/音频入口，用户只能再次选文件，导致把 PCAP 直接传给 FFmpeg；导航还会卸载结果页，丢失已完成的分析。插件进程隔离不意味着业务流程必须隔离。

本轮不改原 RTP/H.264/H.265/音频解码器、不改已安装签名插件文件。核心新增报告联动与内容寻址产物交接，继续调用既有独立插件动作。

1. PCAP 扫描结果每路有“深入分析此流”按钮，自动填入流 ID 与来源抓包产物。
2. 指定流分析完成后，视频出现逐帧/QP/运动矢量和 NALU 语法/HEX；音频出现质量分析及格式/区间导出。样本预览也通过宿主校验的产物显示。
3. 视频深度插件收到原始 `sample.h264` / `sample.h265`，不是抓包文件，也不是转码的预览文件；音频质量/导出插件收到该路解码的 WAV。
4. 目标插件没有安装或禁用时，提示到管理页处理，来源结果保留。任务交接前与执行时分别核对产物摘要、目标动作和声明文件输入。
5. 当前会话的页面参数/结果不随导航卸载，提供返回来源与上一份结果；跨插件填参完成前禁止执行，避免使用目标页面此前的旧输入。密码字段在离开或执行后清空，历史参数快照不保存密码。
6. 流入口支持按流 ID、编码和地址搜索。一次展示前 100 个匹配流，支持多于两路，不只显示最前面的流。
7. 旧插件 v2 报告在查看时可只读补充联动入口，原始 `result.json` / HTML 不改写；样本缺失时显示提示。元数据使用缓冲流式反序列化，跳过 RTP/NALU 明细，上限 512 MiB。

## 本轮证据

- 真实用户样本 `206卡顿问题(1).pcap`：86,419,252 B，识别 9 路；视频 `stream-0003` 和 PCMU 音频 `stream-0001`。
- 从本机已经安装且验过签名/摘要的插件执行扫描、视频选流、video-worker 逐帧画面/块证据、NALU 语法、音频选流、质量分析和 MP3 导出。所有报告和样本写入新建临时目录；成功后清理，不修改原抓包、用户报告或插件注册表。
- 宿主 22 项单测：H.264/HEVC 与音频样本隔离、扫描未选流不误认已深入分析、600 路各自可寻址、重复适配不重复生成区块、Linked 文件不重复导入、未声明字段/越界/篡改拒绝、误送 PCAP 给视频/音频的明确指引，以及既有安装/签名等回归。
- 核心桌面 3 项只读报告/导出/联动失败保留结果测试，兼容桌面 10 项旧功能/报告测试；两个前端构建通过。
- 独立无头浏览器（模拟 IPC）验证 14 个入口布局，以及 PCAP→视频深度、PCAP→音频质量/MP3 格式选择、返回来源和恢复扫描结果。没有控制用户浏览器或电脑桌面。

复测：`node scripts/verify-plugin-workflows.mjs`，或将 PCAP 路径作为第一个参数。需要本机已经安装 PCAP、H.264/H.265、音频、视频深度与 FFmpeg 运行时。该真实抓包测试必须显式运行；普通 `cargo test` 不会自动读取用户抓包。
